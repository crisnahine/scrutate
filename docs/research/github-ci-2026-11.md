# GitHub Actions CI for scrutate: what it should contain (November 2026)

Research date: 2026-11-11. Every claim links to the primary source it came from. Versions and dates are given where the source states them. Release pages on github.com show day and month but no year; where a year is given below for those, it is the year of the page's copyright footer (2026) and is marked "(2026)". The scrutate side comes from `.github/workflows/ci.yml`, `benchmarks.yml`, `release.yml`, `.github/actions/scrutate/action.yml`, `rust-toolchain.toml` (1.99.1), `Cargo.toml` (`[patch.crates-io] ignore`), `fuzz/Cargo.toml`, `bench/baseline.json`, `packaging/README.md` and `docs/RELEASING.md`. None of the workflows has run.

## What this means for scrutate

1. **The musl jobs fail on the first run.** `dtolnay/rust-toolchain@stable` adds `x86_64-unknown-linux-musl` to the `stable` toolchain, but `rust-toolchain.toml` outranks the default toolchain ([rustup overrides](https://rust-lang.github.io/rustup/overrides.html)), so cargo runs 1.99.1, which rustup installs on demand ([rustup 1.28.1](https://blog.rust-lang.org/2025/03/04/Rustup-1.28.1/)) with only the components and targets the file lists. The file lists no targets. This breaks `ci.yml` job `musl` (lines 81 to 86) and the two musl rows of `release.yml` (lines 20, 22, 29 to 31). Fix: put the targets in `rust-toolchain.toml`, or run `rustup target add` from the repository root, or switch to `actions-rust-lang/setup-rust-toolchain`, which reads the file and adds its `target` input to that toolchain ([README](https://github.com/actions-rust-lang/setup-rust-toolchain)).
2. **Two more steps fail as written.** The `audit` job needs `checks: write` to create its check ([audit-check README](https://github.com/rustsec/audit-check)) and the workflow grants only `contents: read` (`ci.yml` lines 9 to 10). The `leaderboard` job runs `pip install uv` on the system Python 3.12 of `ubuntu-24.04` (`benchmarks.yml` line 33), which is marked externally managed and refuses `pip install` ([runner-images #10781](https://github.com/actions/runner-images/issues/10781)). Use `astral-sh/setup-uv` (v10.3.3, 28 Oct (2026), [releases](https://github.com/astral-sh/setup-uv/releases)) or `actions/setup-python`.
3. **Every action reference is one or more majors behind, and none is pinned.** checkout v4 (latest v7.0.1), upload-artifact v4 (v7.0.2), download-artifact v4 (v8.0.2), setup-python v5 (v7.1.0), attest-build-provenance v2 (v4, and new code should use `actions/attest`), action-gh-release v2 (v3.0.4). GitHub's guidance is a full-length commit SHA ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)), and since 2026-10-28 a workflow lockfile `.github/workflows/actions.lock` made with `gh actions-lock` does the same job while keeping readable tags ([changelog](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/), [how-to](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)). See [section 2](#2-action-versions-and-pinning).
4. **The benchmark gate cannot fail.** `bench/baseline.json` was recorded on a 2-core Xeon VM, not on a 4-core `ubuntu-latest` runner, so the `bench` job compares two machine types. The `leaderboard` job skips its gate because `bench/results/ci/leaderboard-baseline.json` does not exist. Both run weekly, not on pull requests, so neither can "block the change" as R-14.15 says. Hosted Linux jobs may also land on different cloud providers ([about hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)). For a regression signal on shared runners, count instructions: CodSpeed's simulation mode runs any executable through `codspeed exec`, but not static binaries and not child processes ([CodSpeed CLI](https://codspeed.io/docs/cli)). See [section 6](#6-benchmark-regression-tracking).
5. **Lock down `release.yml` before the first tag.** It grants `contents: write`, `id-token: write` and `attestations: write` to every job at the top level (lines 7 to 10), including the eight build jobs that compile third-party crates. Move them to the one job that needs each, add a `release` environment with required reviewers (free on public repositories, [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)), turn on immutable releases (GA 2025-10-28, [changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)) and protect `v*` tags with a tag ruleset. With immutable releases the release has to be a draft until every asset is attached ([immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)).
6. **Runner labels are all valid today, with one date to plan for.** All six labels in the matrix exist and are standard runners, free on public repositories ([runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). `macos-latest` is now macOS 26 on arm64 with 3 M1 cores and 7 GB ([runner-images](https://github.com/actions/runner-images)). GitHub ends x86_64 macOS support when the macOS 15 image retires in fall 2027 ([changelog 2025-09-19](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/)). `macos-26-intel` is listed and has no retirement date yet.
7. **Free supply-chain checks that are missing:** Dependabot for `cargo` and `github-actions`, dependency review (v5, free on public repositories), CodeQL for Rust (GA 2025-10-14, default setup, no build), OpenSSF Scorecard, zizmor, `cargo deny`. Secret scanning already runs on public repositories at no cost ([about secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/about-secret-scanning)). See [section 3](#3-supply-chain-and-security-checks).
8. **The composite action has a template injection.** `action.yml` lines 16 and 31 put `${{ inputs.version }}` and `${{ inputs.args }}` straight into the shell script. GitHub's guidance is to pass such values through environment variables ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)), and zizmor flags it as `template-injection` ([audits](https://docs.zizmor.sh/audits/)).
9. **crates.io stays blocked for reasons CI cannot fix.** The `.crate` limit is 10 MB ([cargo publishing](https://doc.rust-lang.org/cargo/reference/publishing.html)), and the model is 14.6 MB. When it is unblocked, trusted publishing works from GitHub Actions through `rust-lang/crates-io-auth-action`, but the first release must be published by hand ([crates.io update, 2025-07-11](https://blog.rust-lang.org/2025/07/11/crates-io-development-update-2025-07/)). PyPI trusted publishing has no such catch and adds PEP 740 attestations by default ([pypi-publish README](https://github.com/pypa/gh-action-pypi-publish)). `release.yml` builds wheels but never publishes them.
10. **No merge queue.** It is available only in public repositories owned by an organization ([merging with a merge queue](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue)). `crisnahine/scrutate` is a personal account, so use a branch ruleset with required status checks instead.

## 2. Action versions and pinning

GitHub's guidance ([secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)): pinning to a full-length commit SHA "helps mitigate the risk of a bad actor adding a backdoor", a tag "can be moved or deleted", and a workflow lockfile "supersedes SHA pinning for repositories that adopt it". Dependabot "will not create alerts for actions pinned to SHA values" but still opens version-update pull requests. Since 2025-08-15 an allowed-actions policy can require full SHA pinning ([changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/)).

Workflow lockfiles went to public preview on 2026-10-14 and GA on 2026-10-28, on Free plans too ([changelog](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/)). The file is `.github/workflows/actions.lock`, made with `gh extension install github/gh-actions-lock` then `gh actions-lock`. Dependabot regenerates the lockfile entry in its bump pull request. Local `uses: ./...` actions are never locked; the tool can migrate them to the `$/` self-repository syntax ([how-to](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)). A reusable workflow in another repository is covered "by the lockfile of the repository where they're defined".

## 6. Benchmark regression tracking

What the sources say about variance on shared runners:

- GitHub's runner pages say nothing about performance consistency. They do say hosted Linux jobs are "automatically scheduled across available cloud providers" ([about hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)), so two runs of `ubuntu-latest` may not share hardware.
- github-action-benchmark reports "about +- 10~20%" on its own examples, more with file I/O, and suggests self-hosted runners if that is too much ([README](https://github.com/benchmark-action/github-action-benchmark)).

| Option | Measures | Works for a CLI walking a file tree? | Source |
| --- | --- | --- | --- |
| CodSpeed simulation (`codspeed exec -m simulation -- <cmd>`) | Simulated CPU cycles from instruction counts and cache misses (Valgrind fork). System calls are excluded from the score. | Partly. Any executable works, but "Statically linked executables are not currently supported" (so the glibc build, not musl) and child processes are not followed. A tree walk is mostly `open`/`read` syscalls, which are excluded, so the score tracks parsing and matching, not I/O. Linux only (Ubuntu 22.04, 24.04, 26.04, Debian 12). Under mission section 14, any of these is fine for regression tracking; none of the shared-runner numbers should reach LEADERBOARD.md.

## 9. Order of work on the day the repository goes public

1. **Make the existing workflows pass.** Add the musl targets to `rust-toolchain.toml` (or `rustup target add` in the repository), give `audit` `checks: write`, replace `pip install uv` with `setup-uv`, add `timeout-minutes` and a `concurrency` group, shorten artifact retention. Run `ci.yml` once and flip R-6.1, R-6.12 and R-9.10 only from the recorded run.
2. **Lock down before the first tag.** Per-job `permissions:` in `release.yml`, bump every action to its current major and run `gh actions-lock`, fix the composite action's injection, add `.github/dependabot.yml` (`cargo`, `github-actions`), a branch ruleset on `main` with required checks, a tag ruleset on `v*`, a `release` environment, immutable releases with draft-then-publish, repository push protection, CodeQL default setup.
3. **Then the first release.** Tag `v0.1.0`, check the attestations with `gh attestation verify`, attest the SBOM with `actions/attest`, add a PyPI publish job with trusted publishing, then send the Homebrew, Scoop and winget updates (by hand the first time).

What can wait: zizmor, Scorecard, dependency review and `cargo deny` (each one job, add in the week after); the MSRV job and an `extra-langs` build; ClusterFuzzLite (start by replaying `fuzz/regressions/` on nightly); instruction-count benchmarks on pull requests (CodSpeed simulation or Bencher with hyperfine JSON) and a baseline recorded on the runner type; coverage, nextest, typos; crates.io (blocked on model size and the `ignore` patch); semver checks (only after a crates.io release).
